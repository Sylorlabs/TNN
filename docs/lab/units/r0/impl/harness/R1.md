## 1. What R-1 freezes (and only this)

The frozen R-1 text defines, for text/code byte streams:

- A span **occurrence's consequence label** = **(a)** recall success of the span in a
  probe episode **+ (b)** downstream discrimination consistency — the span's presence
  predicts the same probe outcome across occurrences.
- **purity(span)** = majority-label fraction over occurrences.

That is the entire frozen semantics. The frozen text does **not** specify the concrete
probe task, the prediction rule, or the outcome encoding. This module therefore does
**not** invent a reference predictor or a reference downstream predicate: the
**battery manifest** defines the specific hidden probe and the expected outcome
**before execution**, and the battery supplies per-occurrence observations.

## 2. Definitions

- **Byte stream** `S`: a finite sequence of bytes (a probe-scale unit, ≤ 2²⁰ bytes —
  see §6 scope note). Text and code are treated identically: bytes are bytes.
- **Span**: a contiguous byte range `S[o .. o+L)` with `MIN_LEN ≤ L ≤ LMAX`
  (defaults: `MIN_LEN=3`, `LMAX=64`).
- **Span content** `C`: the byte string itself. Two spans with byte-identical content are
  occurrences of the same span.
- **Occurrence**: a start offset `o` with `S[o..o+L) == C`. Occurrences are always listed
  in ascending offset order. Singleton spans (k < 2) are **not labeled**.

## 3. Consequence label of a span occurrence

For a span content `C` with occurrences `o_1 < o_2 < … < o_k` (k ≥ 2), the battery's
preregistered manifest supplies, per occurrence `o_j`:

- `a_j ∈ {0,1}` — recall success of the span in its probe episode (per the manifest's
  probe definition);
- `q_j ∈ {0,1}` — the downstream probe outcome for the occurrence (per the manifest's
  probe definition and expected-outcome rule).

### (b) Downstream discrimination consistency — per span (cross-occurrence)

`b = 1` **iff** `q_j` is identical for all occurrences `j = 1..k` — i.e., the span's
presence predicts the same probe outcome every time it occurs. Otherwise `b = 0`.

`b` is span-level by construction: "the span's presence predicts the same probe
outcome across occurrences" is inherently a cross-occurrence property.

### Label encoding

`label(o_j) = a_j * 2 + b ∈ {0, 1, 2, 3}`, i.e.:

| label | (a) recall | (b) consistent |
|-------|-----------|----------------|
| 0 | fail | no |
| 1 | fail | yes |
| 2 | ok | no |
| 3 | ok | yes |

## 4. Purity

For span content `C` with `k` occurrences and label counts `c_0..c_3`:

> **purity(C) = max(c_0, c_1, c_2, c_3) / k** — the majority-label fraction.

Reported in millipoints (e.g., 916 = 91.6%). Because `b` is span-constant, at most two
labels are ever populated for one span, so purity ≥ 0.5 always; the informative range
is how far above 0.5 it sits.

## 5. Exact operational procedure (what `r1_label.zag` does)

1. **Enumerate**: scan positions ascending, lengths ascending (`MIN_LEN..LMAX`); insert
   each `(FNV-1a-64(content), L)` into a 65,536-slot open-addressing table stored as
   `[]u8`-backed little-endian cells (slot stride 24 B: content hash u64 @0, len i32 @8,
   first start i32 @12, count i32 @16); verify slot hits by full byte comparison (hash
   collisions never merge distinct contents). Table-full before scan end sets
   `truncated=1` (deterministic; reported, never silent).
2. **Occurrences**: for each distinct content with count ≥ 2, rescan the stream for exact
   byte matches, ascending; cap `R1_MAX_OCC = 1024` (overflow sets the trunc flag cell).
3. **Aggregate**: take the battery's per-occurrence `(a_j, q_j)` observations; compute `b`
   via §3, tally `c_0..c_3` via the label encoding, compute purity via §4.
4. **Test-both leg (R-7)**: purity mode 1 = recall-only variant (majority over `a`
   alone). The mode is an input; varying it is a test-both leg, not a redefinition.
   Frozen default is mode 0 (majority-label).

## 6. Parameters (defaults; test-both legs may vary them)

`R1Params { min_len=3, lmax=64 }`. Per prereg R-7 the redo runs test-both legs on:
**purity definition** (majority-label vs the recall-only variant), **promotion
thresholds**, and **inventory size**. The legs vary the parameters; they do not change
this definition without a dated amendment.

## 7. Scope

This reference implementation runs on **probe-scale units (≤ 2²⁰ bytes)**. It is not
run as one pass over the 9MB corpora: battery crews invoke it per probe episode
(training units, hidden tests, hard-grounding probes). Full-corpus labeling would be a
different (and unneeded) computation.

## 8. Worked reference (from `driver r1test`, byte-identical across runs)

Synthetic stream `S = "abcababcab"`, `min_len=2`, `lmax=4`. Deterministic grouping finds
`"ab"@[0,3,5,8]`, `"bc"@[1,6]`, `"cab"@[2,7]` (offsets verified exact, ascending).
The hardcoded "battery manifest" supplies preregistered observations:

- `"ab"`, recall=`[1,1,0,0]`, outcome=`[1,1,1,1]` → b=1, labels `3,3,1,1` →
  `c1=2,c3=2`, purity **500**. (Recall-only variant: also 500.)
- `"bc"`, recall=`[1,0]`, outcome=`[1,0]` → b=0, labels `2,0` →
  `c0=1,c2=1`, purity **500**.
- `"cab"`, recall=`[1,1]`, outcome=`[0,0]` → b=1, labels `3,3` →
  `c3=2`, purity **1000**.
- Singleton input → zero label counts, purity 0 (not labeled).

The mechanism behaves as specified: spans whose occurrences' probe outcomes agree get
the consistency bit; spans whose occurrences disagree lose it; purity is the
majority-label fraction. This is the ground truth the redo's batteries score against —
with the probe task itself defined by each battery's preregistered manifest.

## 9. What this definition does NOT claim

- It does not specify the concrete probe task or outcome encoding — that is the
  battery manifest's job, recorded before execution. (Flagged ambiguity, not silently
  resolved: an earlier draft installed an invented reference predictor and an
  ASCII-alphabetic downstream predicate; both were removed.)
- Purity is a property of the stream under the battery's preregistered probes, not a
  score of any arm.
- It does not claim any particular downstream task is "the" task of interest.

## 10. Toolchain note

`r1_label.zag` uses `[]u8`-backed little-endian cells for every table (ZNC-2026-09-19-001 /
ZNC-2026-09-21-004: 3+ sequential `[]i32`/`[]i64` stores corrupt). The `STORESEQ`
probe in `driver.zag` readback-verifies every remaining store pattern.
