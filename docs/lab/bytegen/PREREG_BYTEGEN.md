# BYTEGEN — Byte Generation Strategy: survey, forced-other, head-to-head (PREREG, frozen 2026-09-23)

Micah's question: how does TNN generate its bytes — parallel, autoregressive, what? And what happens when you force the other on it?

## 1. Survey findings (with code cites)

No current native-lab generative path is autoregressive in the LLM sense
(byte n conditioned on generated bytes 0..n-1 as data). No path is fully
parallel either. The universal pattern is **stateful sequential rendering**:

| Path | File | Strategy |
|---|---|---|
| Audio imagination (field) | `tnn-lab/imagination/src/field.zag::f3_synth` (line 932) | Plan-rendered: spectral plan in `ar` cells → per-frame (500 samples) per-bin harmonic accumulation via sine LUT. Phase `pha` carries across frames (fixed deterministic recurrence). Generated samples do NOT feed back into later generation. |
| Audio imagination (v2) | `tnn-lab/imagination/src/imagine.zag::j2_synth` (line 3122) | Same pattern: plan + carried phase state, no output feedback. |
| Audio V10 forks (ARTIC, PARADD, SPECSTAT) | `~/workspace/aud_v10/fork_a`, `fork_paradd`, `fork_specstat` | Sample loop with continuous state (phase accumulators, memory-bearing IIR filters). "Parallel" in PARADD = parallel voice channels, NOT parallel byte generation. |
| Dialogue | `tnn-lab/dialogue/dialogue.zag::do_compose` (line 1302) | Template slot-filling from retrieved facts — whole utterance assembled from a plan, no byte-level feedback. Closest to parallel/planned. |
| Image | `tnn-lab/imagination/design/render.zag::r_one` | Theme-based raster from plan. |

**Verdict: TNN generates bytes by rendering a plan through carried deterministic
state — neither true-autoregressive nor true-parallel.** The forced-other
experiment must therefore build BOTH extremes, since neither currently exists.

## 2. Experiment: forced extremes on one task

**Task:** 30 s mono 44.1 kHz 16-bit WAV from a FROZEN spectral/scene plan
(reuse a frozen V10-era plan fixture; both forks render the same plan).

**Fork AR (true autoregressive):** byte/block n is computed from a function of
the previously GENERATED output bytes 0..n-1. The generator must close the
output→input loop: e.g. frame t's synthesis parameters are derived from an
analysis of the rendered mix of frames < t (a genuine feedback path), not
merely from carried phase. If early output drifts, later output must react
to the drifted bytes, not to the plan alone.

**Fork PAR (true parallel):** every sample is a pure function f(plan, t) with
ZERO carried sequential state — no phase accumulators, no IIR memory, no
frame-to-frame carry. The whole block is computable in any order.

Both forks: pure Zag (pinned znc `~/workspace/tnn-lab/toolchain/bin/znc_linux_x86_64_abed8aa1`),
zero RNG in the render path (deterministic hash streams OK), byte-identical
reruns proven by `cmp` across two renders.

## 4. Red team (blind, after builds)

- **RT-LONG:** long-range dependency traps — plans where a decision at t=1 s
  constrains content at t=28 s (key/mode consistency, call-and-response).
  Hypothesis: PAR fails these (no mechanism to carry the constraint except
  the plan itself — which tests whether plan-expressiveness substitutes).
- **RT-CASCADE:** perturb one early rendered frame (bit-flip in the mix
  buffer at t=3 s, within-fork fault injection) — does AR derail permanently
  (error cascade) or recover? Does PAR even notice?
- **RT-EDGE:** plan with a discontinuity the plan itself doesn't resolve
  (scene cut at t=15 s). Which strategy degrades more gracefully?
