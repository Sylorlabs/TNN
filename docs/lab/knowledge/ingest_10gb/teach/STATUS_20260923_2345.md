## Pure-Zag merger: merge_zag.zag — PROVEN

**Location:** `tnn-lab/knowledge/ingest_10gb/teach/merge_zag.zag`
(compiled with `toolchain/bin/znc_linux_x86_64_abed8aa1`)

**What:** k-way merge of key-sorted facts.dat shards. Record layout
`[1B kind][2B key_len BE][4B text_len BE][key][text]`. Merge order is
(key_bytes ascending, shard_index ascending) — the same total order as
merge_facts.py's heap on (key, shard_index). Zero RNG. Up to 16 shards.

**Proof (2026-09-23 ~23:15 UTC):**
- Re-merged the 8 physics sub-shards (588,421 records, 635MB) with
  merge_zag_bin.
- Output SHA256: `3b454f66546193683906ca29a21a972778abc9b907953edff254253dc2f45fff`
- Python merge SHA (manifest): `3b454f66546193683906ca29a21a972778abc9b907953edff254253dc2f45fff`
- **BYTE-IDENTICAL.** Smoke test on 5-record 2-shard fixture also byte-identical.
- Speed: 94s wall (8.6s CPU) vs Python's ~45 min for the same merge.

**Bugs found during development (both fixed):**
1. `mg_refill` early-returned `blen` when `avail>=need` WITHOUT shifting the
   remainder to buf[0]; the caller parsed the head record at buf[0] and got
   stale bytes → infinite replay of the first record (754MB from 5 records).
   Fixed with `mg_ensure`: returns the byte offset where the `need` bytes
   start; compacts to front only when I/O is required; caller parses at the
   returned offset. (An intermediate always-compact fix was correct but did
   8MB memmoves per record — far too slow.)
2. None in the merge order logic; the (key, shard_index) tie-break matched
   Python on the first try.

**Recommendation:** use merge_zag_bin for the run-1/run-2 production merges
(proven byte-identical, 30x faster, pure-Zag). Verify the final
facts_run1.dat SHA against a Python merge if time permits.
