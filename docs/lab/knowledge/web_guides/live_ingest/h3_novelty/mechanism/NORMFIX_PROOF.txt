# Norm-fix verdict-neutrality proof (2026-09-23)

The mechanism crew found a latent bug in novel.zag's norm_into: fold_byte
also folded byte values 192..222 (except 215) as if they were Latin-1
capitals. On UTF-8 input those bytes are multibyte lead bytes, so the fold
corrupted them instead of lowercasing (e.g. C3 -> E3, producing malformed
UTF-8 in normed text).

Claim verified before fixing: every load-bearing input byte of the official
battery is pure ASCII, so the 192..222 branch never fires:
  - teach/*.txt: 0 non-ASCII bytes (grep -cP '[^\x00-\x7F]' all six files)
  - fixtures: all S|/F|/I| lines pure ASCII; the only non-ASCII bytes in any
    fixture are the em-dash (E2 80 94) in TITLE: lines, which are metadata
    (never classified, never matched against K). None of E2/80/94 is in
    192..222, so the fold never fired on them either.

Fix (in the committed novel.zag): fold_byte now folds ASCII A-Z only;
non-ASCII bytes pass through unfolded. Character-model comment updated.

Proof of verdict-neutrality:
  - Full 14-corpus official battery run with the UNFIXED binary (pass A)
    and with the FIXED binary (pass B): `diff -rq A B` -> rc=0, zero
    differences across all 73 files (K_PIN.txt, kfile.txt, 14 .input files,
    14 corpora x {report,audit,installs,withholds}.txt, SCOREBOARD.txt).
  - RT2 16-corpus re-attack with the fixed binary: 16/16 scoreboard match;
    the only byte difference vs the unfixed run is F1_translation's
    installs.txt normed-text rendering (fixed = valid UTF-8, unfixed =
    malformed E3-lead bytes). All 5 design breaks reproduce identically.

Conclusion: the fix is verdict-neutral on the official battery. Committed
source carries the fix.
