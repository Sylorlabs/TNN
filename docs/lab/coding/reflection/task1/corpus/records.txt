@C-ARCH-01
T:ARCH
K:compositional,plan,compose,mechanism,select
A program can be built by composing small mechanisms rather than matching
the whole goal to one memorized template. The planner first chooses which
mechanisms the task needs (a loop, a test, an accumulation), then emits
code for each and joins them. When the goal is novel, no whole template
exists, but the parts are familiar. Composition is what lets a fixed set
of known pieces cover an open-ended set of new tasks.
@end
@C-ARCH-02
T:ARCH
K:recursion,recursive,self-call,base,factorial,depth
Recursion is self-referential composition: a function that calls itself
with a smaller argument, plus a base case that stops the descent. The
factorial pattern is the canonical example: fact(n) = n * fact(n-1),
fact(0) = 1. Whenever a task says "recursive", the plan is a self-calling
function with an explicit termination case, not a loop.
@end
@C-ARCH-03
T:ARCH
K:nested,loop,2d,pattern,triangle,row,column
Two-dimensional output comes from nested loops: the outer loop walks the
rows, the inner loop walks the columns of the current row. A triangle of
height h prints row r with r stars. The inner bound depends on the outer
counter; that dependency is the whole plan. No recursion is needed.
@end
@C-ARCH-04
T:ARCH
K:sentinel,terminator,scan,argv,zero,stop
Some inputs end with a marker instead of a count. The plan is a scan that
stops at the sentinel: walk the arguments, convert each, halt at the first
zero, and never read past it. Counted loops cannot express this; the loop
condition must test the value, not the index.
@end
@C-ARCH-05
T:ARCH
K:filter,predicate,class,digit,letter,string
Filtering keeps only the bytes that satisfy a predicate. Walk the string
byte by byte, test each byte against the class (digit means 48 to 57),
and copy the keepers into an output buffer. The output length is not
known up front; track a write cursor separately from the read cursor.
@end
@C-ARCH-06
T:ARCH
K:accumulator,multi,total,product,sum,output
One pass can maintain several running totals at once: a sum accumulator
and a product accumulator updated in the same loop over 1..n. The plan
emits each total on its own output line. Multi-line output is just
several print steps in sequence; each accumulator is one variable.
@end
@C-ARCH-07
T:ARCH
K:modular,dispatch,divisible,fizzbuzz,branch,remainder
Periodic behavior dispatches on remainders: test n%3==0 and n%5==0 and
branch to the matching word. The combined case (both) must be tested
first, then the single cases, then the default of printing the number.
Order of the branches is load-bearing; the plan fixes it deliberately.
@end
@C-ARCH-08
T:ARCH
K:run,group,encode,count,repeat,scan
Run-length structure is found by grouping: scan the string, extend the
current run while the next byte equals the current byte, then emit the
run length followed by the byte. Two cursors (run start, scan position)
and one emitted pair per group. The final group must be flushed after
the loop ends.
@end
@C-ARCH-09
T:ARCH
K:bitwise,bit,popcount,halve,remainder,loop
Bits are walked arithmetically: while n>0, the lowest bit is n%2 and the
rest is n/2. Counting the set bits (popcount) is one loop with one test
and one halving step per iteration. No bit operators are required;
remainder and division express the same plan.
@end
@C-ARCH-10
T:ARCH
K:revision,diagnose,evidence,compiler,repair,deliberate
A failed build is evidence, not noise. Read the compiler's error, name
its class (type, arity, unknown name, syntax), and revise the plan at the
point the evidence implicates. Blind retry of the same emission is never
a repair; the revision must be traceable to the error text.
@end
@C-ARCH-11
T:ARCH
K:plan,emit,mechanism,select,order,trace
Plan before emitting: the learner first writes down which mechanisms it
will use and in what order, then generates code. The plan is inspectable
and the emission must follow it. If the emission drifts from the plan,
that is a defect in the emitter, caught by comparing the two.
@end
@C-ARCH-12
T:ARCH
K:audit,teach,provenance,log,install,record
Every installed item of knowledge is logged with its provenance: what was
taught, when in the sequence, and a checksum of the content. The audit
lets a later inspection replay exactly which knowledge the learner held
at any point. Teaching without a log is indistinguishable from guessing.
@end
