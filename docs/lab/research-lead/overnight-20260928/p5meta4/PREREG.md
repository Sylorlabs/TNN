# PREREG -- P5-meta4: make fact-replay useless

Branch `ownership`. Successor to `p5meta3`, generated by the queue's
successor rule. **Written before the run** (derived from p5meta3's
implementation; the delta is a single declared change).

## WHY

`p5meta3` found M1 PASS (relevant prior cut acquisition 24.50 -> 3.00)
but M4 FAIL with **ablation cost zero**: deleting all learned machinery
while keeping retained facts cost nothing. The speedup was a fact cache.

The successor therefore removes the cache's advantage **by construction**
rather than by more controls.

## THE SINGLE CHANGE

Acquisition is measured on queries the prior phase **never showed**.

* prior phase shows `q = 0 .. 11`
* acquisition probes `q = 12 .. 21`, mapped into a disjoint input band
  (`pq0 = 100 + (11q mod 37)`, `pq1 = 200 + (17q mod 41)`)

No retained fact can match a probe query, so a fact cache **provably
cannot replay**. Only a mechanism that learned the *mapping* can succeed.

## BAR

* **M4' (decisive)**: if the machinery is real, `RELEVANT` must still beat
  `FRESH` on never-seen queries. If `RELEVANT` degrades to or below
  `FRESH`, the prior was a cache and the p5meta3 result is void.
* **M2'**: `IRRELEVANT` must be neutral.
* **M3'**: `MISLEADING` must be harmful or revised.
* Control: `META_ABLATED` (facts kept, machinery zeroed) must not beat
  `FRESH`, since on unseen queries it has nothing but a non-matching cache.

## PREDICTION (recorded before running)

Prior p5meta3 RELEVANT=3.00 vs FRESH=24.50. If the speedup was a cache,
RELEVANT should now **degrade to or below FRESH**, because the cache can
no longer answer. I predict the sign flip.
