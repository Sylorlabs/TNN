## 1. Implementability in current build

**H-TW**: YES. Forged revokes and `aa` writes are within the existing teacher/ledger API; need only a band-length loop over steps 15–48 in battery.py.

**A8**: YES. Menu-walk is pure battery-side construction; four lie families × four repairs, each family shaped to trip exactly one repair. No new machinery.

**A9**: YES. Multiple identities are already creatable; chorus is a synchronized emission across N identities in one round. Missing: explicit identity-count logging in LEDGER_DUMP (currently implicit).

**A6**: YES. Round-7 residue is a battery construction (plant claim in rounds 4–6, launder support to phase-2 learner rows, omit from round-7 teacher). No new machinery.

**D-TW**: NO. Requires recomputing contradiction from pre-`aa` transcript — missing a replay/snapshot API in teacher.zag; the current build only exposes the post-`aa` ledger state.

**D-ESCROW**: NO. Needs a `provisional_window` bit per row and a gate check at promotion — no such field exists in the current ledger schema.

**D-STATELESS**: YES. This is a verification claim, not a new arm; you confirm re-arm by checking `arm_step == fire_step` in existing LEDGER_DUMP output.

**D-COST**: NO. Requires a learner-side repertoire hash the teacher cannot forge — no cost-function slot or non-mintable weight field in the current ledger.

## 2. Top 5 by feasibility × information value

1. **H-TW**: Highest live-hole sharpness, fully implementable now, directly tests whether `aa` can override contradiction.
2. **D-TW**: The paired patch — even if not fully automated, a manual replay of pre-`aa` bytes answers the same question and closes the biggest gap.
3. **A8**: White-box menu audit, fully implementable, immediately reveals repair latch/robustness structure.
4. **A6**: Round-7 kill-bar test, implementable, uniquely probes the one strategy aimed at promotion-bar failure.
5. **A9**: Chorus test, implementable, tests whether the evidence rule is already history-weighted (cheap yes/no with large design implications).

## 3. Most important missing hypothesis

**Silent teacher impersonation via learner-owned ledger rewrite.** None of the listed hypotheses test what happens when the learner itself — not a liar arm — rewrites or extends teacher-signed rows using keys or formatting it already possesses. The current build has no separation between "teacher-signed" and "teacher-formatted-but-unsigned" fields in the ledger. A learner that can append to, reformat, or synthesize rows in the teacher's voice (without forging the teacher's signing key) would bypass every defense that assumes the teacher channel is read-only. D-ESCROW partially addresses silence but not impersonation; H-TW addresses `aa` forgery but not row forgery. The single highest-value addition is a **row-origin attestation** hypothesis: can the learner mint a row that looks teacher-signed enough to pass evidence-algebra checks, and if so, does any current repair catch it? This should be prioritized over C0/C1 dynamics arms, which are interpretive rather than structural.
