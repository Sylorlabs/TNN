# R33-N15 preservation/additive microlearner diagnostic

This is a bounded native-Zag mechanism discriminator, not a recovered R27 continuation and not a promotion experiment.

It tests the specific stability-plasticity hypothesis motivating the proposed R27.1 direction: ordinary shared rewriting may gain new behavior by damaging previously correct behavior, while transactionally preservation-gated updates or zero-initialized additive specialists may improve the frontier.

The synthetic parent is trained only on an old training population. Every arm starts from exactly the same parent. New learning sees only new training examples. Preservation arms compare proposed updates against a fixed set of 96 old *training* anchors referenced to the original fork. Old/new probes are evaluator-only and are never used to fit, accept, reject, gate, stop, or retry an update.

Additive specialists begin with all-zero weights and therefore have zero behavioral contribution at the fork. Their gate is a generic two-prototype Manhattan-distance comparison estimated from unlabeled old and new training inputs; no task id, probe membership, evaluator truth, or hidden success bit enters the learner.

The development matrix contains 12 mechanisms across 8 fresh deterministic populations. The selection rule is frozen in CONFIG.json before development execution. Validation and confirmation use disjoint untouched seed namespaces and fixed controls. A failed development gate is retained as a negative result; holdouts may still run under the predeclared fallback rule but cannot be called qualification.

All arm/population rows retain fork/final old correctness, pointwise old losses/rescues, fork/final new correctness, new gain, proposal/accept/reject/skip counts, final training-anchor loss, and parent update count.

The holdout evaluator is native Zag in the same frozen binary. It accepts any non-frozen selected arm, including fallback arm1, but never duplicates an arm already present in the fixed control set [0,1,4,8]. Validation receives the native development-gate bit as an explicit upstream input. Confirmation is callable for qualification only when the native validation gate passed. A zero upstream bit deterministically forces the holdout gate to fail while still permitting preregistered exploratory validation after a development failure.

Validation and confirmation use the same frozen gate. Across each 12-population holdout, the selected arm must have positive new gain in every population, maximum final-old deficit <=4, maximum pointwise old_lost <=8 in any population, total old_lost <=48, and total new_gain >=192. It must retain at least half of ordinary shared rewrite's total new gain while incurring at most one quarter of arm1's total old_lost, and its total new gain must exceed strict shared preservation arm4. If the selected mechanism is additive+preservation arm10/11, it must also retain at least half of additive-medium arm8's total new gain while incurring at most half of arm8's total old_lost. These are prospective frontier constraints, not post-hoc score selection.

Stage identity is frozen between exposures. The sole development invocation must settle before any validation invocation. Its exact native `N15_DEV_SELECTION,<arm>,<gate>` line, complete stdout hash, selected binary hash, and source/config hashes are written into a development-selection freeze; validation admission is restricted to `validate <that-arm> <that-development-gate>`. The sole validation invocation then settles before any confirmation invocation. Its exact native `N15_HOLDOUT_GATE,N15_VAL,<arm>,<upstream>,<gate>` line and complete stdout hash are frozen; confirmation admission is restricted to the same selected arm and is forbidden unless the native validation gate is1. These inter-stage records are operational binding of native scientific decisions, not an external evaluator.

There is one explicit sentinel outcome. If development emits `N15_DEV_SELECTION,-1,0`, no non-frozen arm had positive aggregate new gain under the frozen fallback. That is a terminal negative result named `DEVELOPMENT_NO_POSITIVE_GAIN_CANDIDATE`. It consumes development and forbids both validation and confirmation; the operator must not substitute an arm, rerank arms, or expose holdout populations. A development gate of0 with a real selected arm `>=1` remains distinct: exactly one preregistered exploratory validation is allowed, its native gate is forced to0, and confirmation remains forbidden.

Each stage is consumed by its first actual invocation regardless of outcome. A development-gate failure may still permit exactly one preregistered exploratory validation, but qualification is forced false and confirmation is forbidden. No failed stage may be rerun, no selected arm may be swapped, and no source, threshold, seed namespace, control set, or resource budget may change after exposure.
